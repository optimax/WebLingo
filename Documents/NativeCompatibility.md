# Native C# portability inventory — M0.6

| Facility | Classification | Notes |
|---|---|---|
| Basic C# classes, structs, primitives | Portable target | Verify Native C# compiler support |
| Exceptions, delegates, generics | Planned | Inventory changes with compiler maturity. The VM catches a built-in's exception and reports it as a runtime error; the core's own code reports errors as results, not exceptions |
| C# records, pattern matching, switch expressions, string interpolation | Planned | Used throughout the compiler, bytecode, runtime and VM (M0.6) |
| System.Collections.Generic (`List<T>`, `Dictionary<TKey, TValue>`, `Stack<T>`, `HashSet<T>`, `Queue<T>`) | Planned | Compiler, verifier, VM (M0.6); `Queue<T>` holds the tasks ready to resume (`WebLingoScheduler`, M0.11.1) |
| System.Linq | Not used | Kept out of the portable core's source (tests use it) |
| `BitConverter.DoubleToInt64Bits` / `Int64BitsToDouble` | Portable target | binary64 values and constants are kept as their IEEE 754 bits |
| Invariant number formatting (`long.ToString`, `double.ToString("R")` with `CultureInfo.InvariantCulture`) | Planned | The text `write` writes for a number (`WebLingoValueFormatter`). The Native C# runtime must give the same text, exactly: the shortest decimal that reads back as the same binary64, in .NET's exponent style (`1E+21`, `1.5E-07`). Relying on .NET for it until then is approved (12 November 2026) |
| `IDisposable` | Planned | A native class's host object (`WebLingoHeap`, `WebLingoNativeClass`, specification, section 3.9), which the heap disposes when the collector frees the instance holding it, or when the execution ends. Native C#'s own disposal contract stands in for it there |
| Invariant numeric format strings (`long.ToString(format, …)`, `double.ToString(format, …)` with `CultureInfo.InvariantCulture`) | Planned | An interpolation's format, `{price:N2}` (`WebLingoInterpolationFormat`, specification, section 3.5). The Native C# runtime must give the same text for the formats the specification lists as kept, their rounding included |
| Invariant date and time format strings, and the calendar (`DateTimeOffset`, `DateTime.DaysInMonth`, `DateTimeOffset.ToString(format, …)` and `DateTimeOffset.TryParseExact` with `CultureInfo.InvariantCulture`) | Planned | A date's members, its text, `d.format(format)`, an interpolation's format of a date, and `DateTime.parse` (`WebLingoMembers`, specification, section 3.2, "Dates and times"). The Native C# runtime must give the same dates and the same text for the formats the specification lists as kept, the invariant culture's names of months and days included |
| `System.Decimal`, its arithmetic, `decimal.TryParse` and `ToString` with `CultureInfo.InvariantCulture` | Planned | Decimals, `1.5m` (specification, section 3.2; the owner's answer, 16 November 2026, .NET's `decimal` until Native C#): the lexer's literals, WLBC's decimal constants and their verification, and the runtime's arithmetic, comparisons, text and formats. The Native C# runtime must give the same results, a 96-bit integer and a scale, as .NET's `decimal` rounds them |
| Invariant number parsing (`double.Parse` with `NumberStyles.Float` and `CultureInfo.InvariantCulture`) | Planned | The lexer's binary64 literals (`WebLingoLexer`), and `Number.parse` (`WebLingoConversions`, `WebLingo.Runtime`). The Native C# runtime must give the same value: the binary64 nearest to the decimal, as IEEE 754 rounds it |
| `System.Text.StringBuilder` | Planned | The disassembler, the lexer's string literals, the text of an array (`WebLingoValueFormatter`), and `WebLingoCollectedOutput` (`WebLingo.StdLib`), which collects a script's output for tests and hosts |
| `volatile` fields | Planned | `WebLingoCancellationSignal`, set by the host, read by the VM |
| `ref readonly` locals and `in` parameters | Planned | The VMs read their instructions where they are, without copying them |
| `ReadOnlySpan<T>` | Planned | A built-in's and a native function's arguments, a read-only view of the VM's registers or slots, never copied (`IWebLingoBuiltinFunction`, `WebLingoNativeFunction`, specification, section 3.9); Native C# needs `ref struct`s for it, or the contract becomes an array, an offset and a count |
| `Math.BigMul(long, long, out long)` | Planned | The VMs' int64 multiplication, whose 128-bit product shows an overflow |
| `Array.Resize`, `Array.Clear`, `Array.Copy` | Planned | The VMs' stacks of frames, and the registers or slots a returning call clears; the bytes of a WLBC file as they are written (`WebLingoBytecodeWriter`) |
| `char.IsSurrogatePair`, `char.IsHighSurrogate`, `char.IsLowSurrogate`, `string.Substring`, `new string(char[], int, int)` | Planned | A string's `length` and indexing count Unicode scalar values (`WebLingoMembers`), over the UTF-16 text a string is kept as; WLBC's strings, which its writer encodes as UTF-8 and its reader decodes itself, without `System.Text.Encoding` (`WebLingoBytecodeWriter`, `WebLingoBytecodeReader`) |
| A string's ordinal searching and replacing (`IndexOf`, `LastIndexOf`, `Contains`, `StartsWith`, `EndsWith` and `Replace` with `StringComparison.Ordinal`), `Split(string)`, `Trim`, `TrimStart`, `TrimEnd`, `ToUpperInvariant`, `ToLowerInvariant` and `string.Join` | Planned | Strings' methods (`WebLingoMembers`, specification, section 3.5, "String methods"). The Native C# runtime must give the same results, the invariant culture's case mapping of each UTF-16 code unit and .NET's white space included |
| `System.Text.RegularExpressions` (`Regex` with `RegexOptions.CultureInvariant` and a match timeout, never `RegexOptions.Compiled`) | Planned | Regular expressions (`WebLingoHeap`, `WebLingoMembers`, specification, section 3.6, "Regular expressions"; the owner's answer, 16 November 2026, .NET's syntax, its engine used now). The Native C# runtime needs an engine that reads .NET's syntax and gives the same matches, its options and its substitutions included, with a limit on time; `RegexOptions.Compiled` would generate CLR code, which the portable core never does |
| `StringComparer.OrdinalIgnoreCase`, `string.Equals(…, StringComparison.OrdinalIgnoreCase)` | Planned | HTTP headers' names, compared without regard to ASCII case (`WebLingoHeaderList`, `WebLingo.Hosting.Abstractions`); the Native C# runtime need only fold ASCII's case there, since a header's name is ASCII |
| `[MethodImpl(MethodImplOptions.AggressiveInlining)]` | Planned | A hint to .NET's JIT on the VMs' arithmetic and comparisons; a compiler that ignores it still compiles the code correctly |
| .NET Task / ValueTask | Adapted only | Not permitted as WebLingo core async contract |
| .NET `CancellationToken` | Not used | The VM's cancellation is WebLingo's own `WebLingoCancellationSignal` (WL-P007) |
| System.Diagnostics.Stopwatch | Adapted | DotNetClock only |
| .NET's clock and local zone (`DateTime.Now`, `DateTime.UtcNow`, `DateTime.Today`, `DateTimeOffset.Now`, `DateTimeOffset.UtcNow`, `TimeZoneInfo`) | Adapted | `DotNetClock`, the PAL's wall clock, and `DotNetTimeZone`, the server's zone and the platform's others, found by their IANA names with `TimeZoneInfo.TryFindSystemTimeZoneById` (`WebLingo.Platform.DotNet`; specification, section 3.2, "Time zones"); the portable core reads the time and the zones through them (`WebLingoExecutionContext.WallClock` and `TimeZone`, specification, section 7.6) |
| System.IO.File, Directory, their `Info` types, FileStream, StreamReader, StreamWriter | Adapted | CLI/bootstrap, and `DotNetFileSystem` (`WebLingo.Platform.DotNet`), the PAL's file system, which `std:fs` reaches (section 7.4); never the portable core; their links' targets, `LinkTarget` and `ResolveLinkTarget`, in `DotNetFileCapabilities`, which follows a site's paths to their real ones (section 7.13, "File capabilities") |
| Platform invoke of Windows's `ole32` and `oleaut32`, unmanaged function pointers (`delegate* unmanaged[Stdcall]`), unsafe code | Adapted | `WebLingo.Windows.Com`, `windows:com` (section 3.10): COM's functions and its interfaces' tables of methods, never .NET's COM interop (`dynamic`, `Type.InvokeMember`, `[ComImport]`), which Native C# will not have; Windows only; never the portable core |
| System.Text.Encoding and its encodings, with exception fallbacks | Adapted | `DotNetFileSystem`'s encodings, named by scripts (`utf-8`, `utf-16`, …), invalid bytes an error. The portable core uses its own codec instead, `WebLingoTextCodec` (`WebLingo.Runtime`): UTF-8, UTF-16, US-ASCII and ISO-8859-1, read and written without `System.Text.Encoding` |
| `System.Threading.Timer`, `Monitor` (`lock`), `Interlocked`, `Volatile` | Adapted | A host's: the ASP.NET Core adapter times a slow client (`WebLingoStreamingResponse`) and synchronizes its own threads. The portable core keeps no timer and takes no lock: an execution's state is its worker's alone, and work done off the worker hands over through the scheduler host's `Post` (`IWebLingoSchedulerHost`) |
| `System.Uri` | Not used | The core decodes a query's and a form's `%xx` itself (`WebLingoHttpObjects`) |
| System.IO.Path | Adapted | Paths and their separators are the PAL's, not the platform's |
| System.Console | Adapted | A host's (the CLI's), never the core's |
| System.Environment | Adapted | The core must not depend on the platform, its line ending among others |
| OS threads (`Thread`, `ThreadPool`), `Monitor` | Adapted | Adapter-only (§7.14); the CLI's clock sleeps while an execution waits for a timer (`Thread.Sleep`, M0.11.1); `DotNetSchedulerHost` runs blocking work on the thread pool and holds the work posted back in a queue that `Monitor` guards (section 7.8) |
| P/Invoke | Adapted | Adapter-only (§7.14) |
| ASP.NET Core | Adapted | Hosting adapter only |
| ADO.NET (`System.Data`, `System.Data.Common`, Microsoft.Data.Sqlite, Microsoft.Data.SqlClient) | Adapted | `DotNetDatabases` (`WebLingo.Data.DotNet`), which `std:db` reaches through `IWebLingoDatabases` (§7.11); never the portable core |
| System.Net.Http, System.Net.Sockets | Adapted | the platform's network, `DotNetNetwork` (`WebLingo.Platform.DotNet`), which `std:http` and `std:net` reach through `IWebLingoNetwork` (§7.2, §7.9) |
| Reflection.Emit | Prohibited | No dynamic CLR codegen in portable core |

**Checks.** Dependency direction is enforced by the project references and by `DependencyTests`; the rows above classified Adapted, Prohibited or Not used are checked on the portable core's built assemblies by `PortabilityTests` (both in `WebLingo.Architecture.Tests`), which fail when the core references such a type or declares a P/Invoke. A new rule for the portable core goes into this table and into `PortabilityTests`. The CI workflow (`.github/workflows/build.yml` at the repository root) runs these tests on both OSes on every push; its first run passed (CI run 1, 12 November 2026, commit `5229806`). The Planned rows are not checked: they record what the Native C# compiler and runtime must provide.
